# The plugin reads its watch list from a file (sub-project 3 of the balance catalogue roadmap)

Date: 2026-09-24. Status: **written while the owner was away**, from the
direction in `2026-09-24-balance-catalogue-and-triage-design.md` ("The plugin
reads its watch list from a file the site pushes, not a compiled include. After
one pug-match rebuild, adding a value is a site-only change."). Every decision
below that the direction did not already make is marked **(proposed)** for the
owner to confirm or overturn.

## Why

pug-match reports the balance inventory (cvars, plugins, watched files and
directories) at every go-live. The cvar, file and directory lists are compiled
in (`plugin/pug-balance-list.inc`, generated from `balance/knobs.json`), so
watching one more value means a plugin rebuild and a deploy to every box. The
catalogue (sub-project 4) wants about 150 values, including weapon stats, and
will grow; it needs the list to be data.

## Design

### The watch file

- Path on each box: `left4dead/addons/sourcemod/data/pug_balance_watch.txt`.
- Written by **the site** (proposed), the same way it writes `cfg/pug_balance.cfg`:
  a writer that checks every enabled box on a timer and in the between-matches
  hook, and rewrites the file only when its content differs. Not a release: the
  list comes from the site's own configuration, and "adding a value is a
  site-only change" is the point.
- Content generated from `balance/knobs.json` today (and from the catalogue once
  sub-project 4 lands), one entry per line:

```
// GENERATED by riversidepug.com from balance/knobs.json. Do not edit.
cvar z_tank_health
file addons/sourcemod/data/l4d_info_editor_weapons.cfg
dir addons/stripper/Roto-AZMod/maps .cfg
weapon weapon_smg SpreadPerShot
```

- `//` comments and blank lines are ignored; an unknown first word is ignored
  (a newer site can add kinds an older plugin skips).
- Limits in the plugin: 512 cvars, 64 files, 16 dirs, 256 weapon keys; names up
  to 64 characters, paths up to 200. Extra lines are ignored and logged once.

### The plugin

- Reads the file at every map start (where it already scans plugins and files),
  into dynamic arrays. The compiled list (`pug-balance-list.inc`) stays as the
  **fallback** when the file is missing, unreadable or has no entries, so a box
  without the file reports exactly what it reports today.
- **Weapon values (new, proposed):** for each `weapon <classname> <key>` entry the
  plugin reads `addons/sourcemod/data/l4d_info_editor_weapons.cfg` (Valve
  KeyValues, section `"weapon_info"` > `"all"` > classname > key) and reports
  `w:<classname>.<key>=<value>`, or `w:<classname>.<key>=default` when the file
  does not set it (the game's own value applies). Map-specific sections are not
  read in this version.
- `BALANCE_END` gains `watch=file|builtin` so the site can see which list a box
  used; older sites ignore the field.
- Version bump; one rebuild and deploy of pug-match.

### The site

- `BAL_ITEM_RE` accepts `w:` items.
- `balanceWatch.ts`: `renderWatchFile(knobs)` and `BalanceWatchWriter` (timer +
  between-matches hook, write-if-different, never in dev mode). The writer's
  target is `transportFor(server, <addons_dir>/sourcemod/data)`.
- **Watch-list changes never ask for triage (proposed).** Adding or removing a
  watched value changes the fingerprint (a new `c:`/`w:` key appears or goes)
  without anything in the game changing. A new detected patch whose only
  differences from the patch its server came from are keys **present on one
  side only** with prefixes `c:`, `x:`, `w:`, `f:` or `d:` is folded into that
  patch automatically at sighting, with no alert. A changed value on a key both
  sides have still counts as a real difference.
- Public change lists already ignore keys present on one side only.

### Rollout

1. Deploy the site (the writer starts writing the file; nothing reads it yet).
2. Rebuild pug-match and ship it as a release. Each box picks up the file at its
   next map. The first sighting after the new plugin carries the same cvar, file
   and dir keys as before (the file lists exactly what the compiled list did),
   so the fingerprint is unchanged unless weapon entries were added; those fold
   automatically (above).

## Testing

- `renderWatchFile` from knobs; file parse rules (comments, unknown kinds,
  limits) mirrored in a TypeScript parser used only by tests against the plugin's
  expected behaviour.
- Writer: writes when missing or different, not when equal, never in dev mode,
  skips busy boxes, per-box failures isolated (fake transports).
- Parser accepts `w:` items; sighting auto-folds a watch-list-only change and
  still opens a pending patch when a shared key changed value.
- Plugin: compiles (`plugin/build.sh`); on the local test server (`~/l4d1-ds-*`)
  with the file present, missing, and with a weapon entry, the BALANCE lines
  carry the expected items and `watch=`.

## Open questions for the owner

1. Site-written file (proposed) versus a file committed to the deploy repo and
   shipped as a release. The direction said "the site pushes"; a release would
   put watch-list changes through review, at the cost of a commit per change.
2. Auto-folding watch-list-only changes: is silence right, or should the admin
   feed get one quiet line ("watch list changed on Dallas; folded")?
