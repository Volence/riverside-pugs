# Balance control panel (piece 4): adjust curated knobs on every server

Date: 2026-09-24. Status: decided by the owner's delegate overnight (the owner asked
for decisions to be made by another agent); awaiting owner review before any deploy.

Parent design: `docs/superpowers/specs/2026-09-23-balance-analytics-design.md`
("Constraints for later pieces"). Pieces 1 to 3 are shipped: every round carries a
`patch_id` from its fingerprint, detected patches raise an admin alert, and the
compare dashboard measures changes.

## Goal

An admin changes a balance knob (for example tank health 8000 to 7500) on a page,
within a safe range, and every server picks it up between matches. The change is an
`announced` patch before any server runs it, so its rounds are tagged with a name
and notes instead of raising "config changed, not through the panel". Any earlier
knob setting can be restored.

## How values reach the servers

Cvars pushed over RCON do not last: the PUG config chain re-runs on every map
(`l4d_ready_server_cfg` -> `rotoblin_pug_4v4_map.cfg` -> shared convars ->
Reloadables -> `local_4v4.cfg`), and every box restarts after a match. So the site
writes a file.

- **The file.** `cfg/pug_balance.cfg` on each enabled server, reached through the
  existing `transportFor(server, cfgDir)` (local on Dallas, FTP on Chicago, sftp on
  Riverside #3 and #4), where `cfgDir` is `addons_dir` with its last segment replaced
  by `cfg`. Content: a header ("generated by riversidepug.com, do not edit; values
  here override the deploy repo; patch <n> <name>") and one `sm_cvar <cvar> "<value>"`
  line for **every adjustable knob**, always the full snapshot. The baseline is
  written as explicit baseline values, never as an empty file, because a value that
  is no longer set stays set.
- **The hook (owner change in the deploy repo).** `exec pug_balance.cfg` as the last
  line of `overrides/left4dead/cfg/rotoblin_pug_4v4_map.cfg` on all boxes, including
  the `nfo/stage` copy. Not in `local_4v4.cfg`: that file also runs for casual
  Hardcore 4v4 (`rotoblin_hardcore_4v4_map.cfg`), which must stay untouched. A missing
  file only prints "couldn't exec", so the hook is safe to deploy before the panel.
- The deploy repo must never contain a `pug_balance.cfg`: it would overwrite the
  site's file on every deploy. The runbook note also warns that re-uploading an old
  `nfo/stage` to Chicago can bring back a stale file (the detected-patch alarm
  catches it).
- **Atomic write.** Write `pug_balance.cfg.tmp`, rename over `pug_balance.cfg`, read
  it back. "Written" means the read-back bytes match. The rename matters because
  `deploy.sh` runs `chown -R l4d:l4d`, which can make an in-place overwrite by the
  `pug` user fail while a rename inside the group-writable `cfg/` still works. Add
  `rename` and `read` to the transport interface where missing.

## Knobs: types, safe ranges, baselines

`balance/knobs.json` cvar entries gain optional fields: `type` (`int` | `float`),
`min`, `max`, `step`, `baseline` (the exact string the PUG chain sets today),
`unit`, `note`, and `pairMax` (a cvar that must be greater than or equal to this
one). A knob is **adjustable** when it has `type`, `min`, `max`, `step` and
`baseline`; the rest stay watch-only. `loadBalanceKnobs` validates: min <= baseline
<= max, step > 0, baseline on the step grid, float baselines written with the
decimals of `step`, pairs valid at baseline. The plugin include is unchanged (cvar
names only).

## Apply flow

1. **Draft.** The panel shows each adjustable knob grouped by `group`: label, current
   value, baseline, range, and a control snapped to `step`. A soft warning shows
   when the draft changes knobs in more than one group ("effects cannot be told
   apart").
2. **Preconditions.** Apply is refused when enabled servers drift (`serverDrift`
   non-empty); the admin can disable a server first. Apply is refused while another
   rollout is still writing.
3. **Expected fingerprint.** Base inventory = the `inputs_json` of the latest
   sighting from a 4v4 PUG round (not `balance_server_state`, which may hold a 2v2
   or auto-tracked casual inventory). Replace the `c:` values of the adjustable
   knobs with the draft values (exact strings to be written), run `withoutIgnored`
   and `fingerprintOf`.
4. **Announced patch.** Created **before** any write, name and notes required. If a
   patch with that fingerprint already exists (a rollback to a known state), reuse
   it and keep its source and name. The confirm dialog shows the diff (knob, old ->
   new) and the servers, and requires typing the patch name.
5. **Rollout.** A `balance_rollouts` row (id, patch_id, values_json, created_by,
   created_at, superseded_at) and a `balance_rollout_servers` row per enabled server
   (state `pending` | `written` | `confirmed` | `failed`, last_error, written_at,
   confirmed_at). A server is written only while `servers.status` is `idle`; a
   `reserved` or `live` server is written by the server release path, before the
   box goes idle and before the after-match restart. A pending write is retried on
   a timer and at site boot. A server that is offline or disabled gets the file when
   it is enabled again; at boot the site compares what each box should have with
   the read-back and rewrites on mismatch.
6. **Confirmation.** When a BALANCE sighting from that server arrives with the
   rollout's expected fingerprint, the server row becomes `confirmed`. Until then
   the panel says "written, awaiting first match" (this can take days on a quiet
   box). A sighting with another fingerprint after the write shows as
   "expected X, saw Y" with the differing inputs (the existing detected-patch alarm
   still fires); a plugin that re-asserts a cvar after the configs run shows up
   here.
7. A new rollout supersedes a pending one. An announced patch that never gets a
   round is labelled "never played" in the Patches tab.

### Known gap

After `!load_4v4p` and before adoption, `servers.status` is still `idle`. A write
landing in that window splits one match across two patches. Per-round fingerprints
keep the data honest. The writer skips a box when the site knows it has players and
retries. Carry-over of a value into a later casual session on a box that did not
restart already happens today and is unchanged.

## Restore and reset

- **Restore** pre-fills the draft from a patch's recorded `c:` values and goes
  through the same apply flow. Only knob values change: the dialog says plugins and
  files stay as they are now, so the result can be a new patch. Values for knobs
  that are not adjustable are ignored, with a note. Historical patches have no `c:`
  values and cannot be restored.
- **Reset to baseline** fills the draft with every baseline.

## Page and API

A new tab **Knobs** in the admin Balance desk (next to Compare and Patches), admin
only (`requireAdmin`), every apply audited with `logAdmin`.

- `GET /api/admin/balance/knobs`: adjustable knobs with current values (from the
  latest applied rollout, else baseline), drift status, the active rollout with
  per-server states.
- `POST /api/admin/balance/knobs/preview`: body `{values}`, returns validation
  errors, the diff, the expected fingerprint and whether it matches an existing
  patch.
- `POST /api/admin/balance/knobs/apply`: body `{values, name, notes}`, runs steps
  2 to 5 and returns the rollout.
- `GET /api/admin/balance/rollouts`: history with per-server states.

## Out of scope

Plugin on/off (later), per-server values, split tests, editing watched files
(`l4d_info_editor_weapons.cfg`, stripper), knobs outside the v1 table.

## Testing

- knobs.json validation: ranges, step grid, baseline, pairs, float decimals.
- File rendering: full snapshot, header, exact value strings.
- Expected fingerprint: equals `fingerprintOf` of a recorded sighting with the same
  values; a changed value changes it; reuse on rollback.
- Apply refused on drift, on invalid values, on an active rollout.
- Rollout state machine: idle write, live server deferred to release, retry,
  read-back mismatch, confirmation on sighting, mismatch report.
- Transport: rename and read for local, and for FTP and sftp against fakes.
- API: admin and non-admin; page render tests.
- **Before ship, on the local test rig:** write the file, change map, check the
  sighting's fingerprint equals the prediction, including a "0.10"-style float.
